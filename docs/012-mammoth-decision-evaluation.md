# 012: Hosted Mammoth decision-model evaluation

**Date:** 2026-10-26

**Status:** In progress. Offline only; no production model or pipeline changes, and no fine-tuning.

This experiment follows [011](011-small-model-match-benchmark.md). Small instruction models did not provide a useful matching cost/quality trade-off. Mammoth is a different experiment: a model trained to produce probability distributions over finite choices through the native System One API, without generating a rationale.

## Provider and scope

- Endpoint: `https://inference.baseten.co/v1/systemone`.
- Model: `decision-models/baseten-mammoth-27b-latest`, a hosted alias rather than a pinned weight revision.
- The [model card](https://huggingface.co/baselabs/mammoth-1) describes a 27B dense Qwen3.5-derived decision model with block-bidirectional full-attention layers, a trained limit of 16,384 tokens, and a decision-specific readout. It is not equivalent to ordinary chat generation from the same weights.
- The user's locally hosted model was listed but its native decision endpoint rejected it as "not a decision model". This evaluation therefore uses the explicitly authorized hosted API.
- The advertised free period ends October 27, 2026 at 23:59 Pacific (October 28 at 06:59:59 UTC). The runner refuses new hosted requests after that deadline and caps new hosted requests at 800 per invocation. Do not extend paid usage without approval.
- Credentials come from `BASETEN_API_KEY` or an owner-readable file named by `BASETEN_API_KEY_FILE`, never a committed value. Reports exclude credentials and request headers.
- Only constructed examples and public article metadata / derived summaries are sent. No article bodies, reader data, credentials, or account information are used. Database connections explicitly enforce read-only transactions.

Native API probability calibration is a claim to evaluate on our tasks, not permission to trust every high-confidence answer. All threshold tables use the raw probability assigned to the chosen option, **not** System One's option-count-normalized `confidence` field.

## Priority order

### 1. Story relationship classification

This is the strongest direct-replacement opportunity: an existing generation call chooses a relation from a small finite vocabulary, while the production graph does not need a generated explanation to insert an edge. Temporal, freshness, cycle and narrative validation must remain deterministic.

1. Run 28 constructed controls covering every relation, unrelated shared actors/themes, insufficient evidence, a publisher-text prompt injection, and a few non-English examples.
2. Run 64 real Story pairs against both Mammoth and a fresh Gemma 4 26B-A4B baseline, with the same summaries and up to 12 anchored reports per Story.
3. Measure relation agreement, uncertainty, false-link behavior on labelled controls and fixed probability thresholds. Do not call agreement with Gemma independent accuracy.

The local snapshot contains 1,747 historical relationship interpretations, all using `classify-relationship@4`. Their labels select a varied sample only: 32 unrelated, 16 follows, eight responds-to and eight related-to cases (including old related decisions with a null type). Fresh Gemma uses `classify-relationship@6`. Historical labels are not the answer key, and the balanced sample does not estimate production prevalence.

### 2. Summary-update materiality

Run 30 constructed examples: material changes, paraphrased corroboration, corrections, status changes, attribution, changing numbers, insufficient metadata and cross-language paraphrases. Compare against fresh Gemma using the existing assessment prompt.

The local snapshot has no historical summary-update assessments, so this is a policy/control test, not a production materiality benchmark. False corroboration is particularly costly: it can suppress a real update. A material verdict still needs the grounded update note and citations currently generated by Gemma; classification alone cannot replace that writing.

### 3. Article-to-Story matching and probability-based fallback

Use the existing 334-article / 145-Story `set-1` replay with its current matching core, candidate limits and anchored evidence:

- **Replacement:** Mammoth selects a candidate or none. An explicit uncertain answer makes no attachment.
- **Probability-0.95 fallback:** accept a non-uncertain Mammoth choice only at raw probability at least 0.95; otherwise ask Gemma. This threshold is fixed before observing these matching results, not selected for a favorable score.

Preserve the full metadata rather than quietly shortening evidence to fit. A hosted length-limit or transport error stops the run; it must not become a "none" decision. Evaluate end-to-end graphs, not only isolated pairs. This remains a previously used development set, not fresh held-out evidence.

### 4. Grounding and publisher stance diagnostics

Run 12 controlled grounding cases and 12 stance cases after the cost-saving candidates. These are lower priority because they add or reorganize work rather than clearly replace a standalone existing call.

- Grounding checks support in the supplied evidence, not truth in the world. Attribution must not become an unqualified factual assertion.
- Stance uses asserts / denies / quotes / discusses. A diagnostic not-mentioned option tests absent claims; it is not a new persisted API enum.
- There is no fresh Gemma comparison for this final diagnostic phase. Do not interpret its report's absent baseline score as a Gemma failure.

## Controls, measurements and limitations

`fixtures/decision-eval/mammoth-controls.json` contains all 82 controls and their expected labels. They were authored by the assistant from repository policies and frozen before model calls. Some relation boundaries deliberately accept two labels. These are simple, often explicit checks, **not independently human-reviewed natural-news gold labels**. Expected labels are never sent to either model.

Reports retain cases, probabilities, decisions, request hashes, token counts and measured HTTP latency. They distinguish constructed-label correctness from real-pair model agreement. Predeclared control threshold tables use 0.90, 0.95 and 0.99; uncertain always means abstain for routing purposes.

The hosted Mammoth deployment and local Strix Halo Gemma deployment use different hardware and serving paths. Comparing their wall latency or generated-token counts does not establish a same-hardware compute saving or future dollar cost. Shared-prefix multi-question inference is a potential capability; these initial one-question requests do not establish its batching speedup.

Gemma requests explicitly use temperature zero, zero thinking budget and disabled thinking, as in 011. Separate content-addressed caches store hosted answers and raw Gemma numeric choices; cached synthetic Story IDs are not copied between replay graphs. Timing aggregates must distinguish measured fresh calls, reused answers and estimates.

## Reproduction

The runner is `scripts/eval-mammoth.mjs`. Provide the Baseten key securely in the environment or in a private external file, and run from the repository root:

```bash
node --env-file=.env --import ./apps/worker/node_modules/tsx/dist/loader.mjs scripts/eval-mammoth.mjs
```

Optional positional stages are `relationships`, `materiality`, `matching` and `checks`. By default they run in that order. Native results and comparisons go to `fixtures/decision-eval/results/`; the matching core also writes its usual report under `fixtures/match-eval/results/`. Intermediate caches live under the already ignored `fixtures/match-eval/cache/mammoth-hosted-20261026/`.

No automatic production rollout follows any score. A recommendation requires error inspection, representative reviewed examples and a justified cost comparison, not just a leaderboard score or a high model probability.
